## 3. 关键分析：为什么不能"看两眼就标"

### 3.1 先验证能不能自动抠图（省掉 90% 的人工判读）

```
全局 alpha>0 比例 = 0.947
每个 bbox 内 alpha 覆盖率 = 0.91 ~ 1.00
每个 bbox 的紧致边界 == 给定 bbox（edge-cut = 0）
```

结论：**透明通道全不透明**，说明 `source.png` 是 30 个图层按顺序合成后的"平图"；bbox 又是紧致的、彼此还互相重叠（比如 S018 有 87% 落在 S001 的框里）。所以：

- 不能用 alpha 单独抠出某个素材；
- 也不能假设"框里只有这一个素材"；
- 但**框是准的**，所以"裁 bbox + 编号 + 上下文放大"就能完成判读。

### 3.2 bbox 重叠矩阵（又是 zIndex 的直接证据）

| 重叠对 | 重叠面积 | 解读 |
|---|---|---|
| S018 ↔ S001 | 22630 px（占 S018 的 87%） | S018 是**画在中央岛前面**的独立小岛 → z 必须比 S001 大 |
| S016 ↔ S002 | 3680 px（占 S016 的 87%） | 云絮压在左远岛下缘前 |
| S029 ↔ S028 | 21735 px（占 S029 的 100%） | 石堆完全落在底边地面带内 → 它是**叠在地面带之上**的前景小件 |
| S028 ↔ S020 | 66297 px | 地面带压过石拱门基座 → 地面带比拱门更靠前 |
| S022 ↔ S001 | 117 px（100%） | 瀑布水光碎片嵌在中央岛瀑布上 |
| S009 ↔ S004 | 81 px（100%） | 高光碎片嵌在右侧大云团里 |

这些"谁压谁"直接决定了 `zIndex` 的相对大小（详见第 4、5 节）。

### 3.3 三级视觉核验（每级解决不同问题）

1. **总览图**（全图 + 红框编号）：解决"每个 id 在画面哪儿"；
2. **接触表**（6×5 单件裁切 + 尺寸标注）：解决"这件东西是什么"，小图用最近邻放大避免糊；
3. **细节图**（带 45% 上下文 + 红框 + 倍率 / 带 100px 网格）：解决"边缘碎片是什么""结构长什么样（好写 description）"。

总共看了 **6 张图**（总览、接触表、细节图、大件细节、锚点复核、边缘放大），每张都是自己用 PIL 现场拼的——原图信息密度不够，逐件裁切才是把"看"变成"可核对"。

## 5. 分层 / 深度 / 视差 / zIndex 的推演规则

### 5.1 分层的判据（按权重从高到低）

1. **遮挡关系**：被前景压住的就是后层（S020 基座被 S028 压 → 拱门 z 21 < 地面带 z 22）；
2. **大气透视**：远景整体偏蓝灰、对比度低、边缘被雾化（S002/S011/S019 明显；S020/S025 颜色饱满）；
3. **细节密度**：同样尺寸下，石块纹理越清楚越靠前（S020 > S015 > S010）；
4. **屏幕位置只作辅助**：天空在上不等于都是远景（S028 在最下且最前），所以没有一票用 Y 坐标判层。

### 5.2 数值区间（对齐规则 5/6/7）

| 层 | depth | parallax | zIndex | 本次实际取值 |
|---|---|---|---|---|
| background | 0.75–1.0 | 0.2–0.5 | 0–9 | depth 0.76–0.96，parallax 0.22–0.46，z 1–9 |
| midground | 0.4–0.75 | 0.55–0.8 | 10–19 | depth 0.48–0.68，parallax 0.56–0.76，z 10–18 |
| foreground | 0–0.4 | 0.85–1.2 | 20–29 | depth 0.06–0.30，parallax 0.88–1.15，z 21–26 |

同层内再按"越远 → depth 越大 / parallax 越小 / z 越小"单调排列，所以 30 条数据放在一起看是自洽的：

```
background:  S004(0.96/0.22/1) … S001(0.80/0.40/7) … S018/S019(0.76/0.46/9)
midground:   S014(0.68/0.56/10) → S015(0.64/0.62/11) → S017/S021 → S023/S024/S026(0.50/0.74/16)
foreground:  S020(0.30/0.88/21) → S028(0.12/1.08/22) → S027/S029(≈0.08/1.10/25) → S030(0.06/1.15/26)
```

### 5.3 zIndex 的"证据链"（不是拍脑袋）

- `S018(9) > S001(7)`：S018 有 87% 面积压在 S001 框内，是画在前面的独立小岛；
- `S022(8) > S001(7)`：水光碎片必须压在瀑布上；
- `S019(9) = S018(9)`：同语汇、同距离的两座边岛；
- `S024(16) > S025(15)`：S024 的右缘压住 S025 的左缘；
- `S026(16) > S015(11)`：右侧草甸平台挡在神殿浮岛下半部前；
- `S028(22) > S020(21)`：地面带盖住石拱门基座；
- `S027/S029(25) > S028(22)`：珊瑚丛与石堆是叠在地面带之上的独立前景件；
- `S030(26)`：最贴边、最靠前的一小条，压在所有前景件之上。

## 6. 自检：6 类硬约束 + 3 项人工复核

生成脚本里带的断言（任一不满足直接 `assert` 失败）：

1. `sprite_id` 集合与 `agent_task.json` **完全相等**（不增不减，30 个）；
2. `category` ∈ {character, creature, prop, architecture, background, terrain, vegetation, effect, UI, other}；
3. `layer` ∈ {background, midground, foreground}；
4. `slug` 匹配 `^[a-z0-9]+(_[a-z0-9]+)*$` 且 **30 个无重复**；
5. `anchor` 同时满足：在图像内 + 在自身 bbox 内 + 等于 bbox 底边中心公式；
6. `depth / parallax / zIndex` 落在所属层的区间内；`relations` 里每个 id 都存在且不等于自己；`confidence ∈ [0,1]`；`needs_review` 的 conf ≤ 0.6。

人工复核：

- **锚点回画**（`anchor_check.png`）：按层上色，30 个十字没有跑偏；
- **UTF-8 抽查**（`read` 工具）：中文正常，无乱码；
- **交付文件复核**（pwsh + Node）：首字节 `7B 0A 20` 无 BOM → `JSON.parse` 通过 → 30 sprites / layers 17:8:5 / 键顺序 = schema。

中途发现并修掉的一个边界问题：锚点最初写 `y + h`，对 S028 会得到 `y=941`，而 941 高的图合法行号是 0–940 —— 已统一改成 `y + h - 1`（最后一行），全部重新校验。

## 8. 踩过的坑（复跑时会再遇到）

1. **`load_workspace_dependencies` 报 EPERM**：运行时的 `node.exe` 被占用无法 unlink。→ 直接用机器上现成的 `<dsh>\im\asr\.venv`（Pillow 13 / numpy 2.5 都齐）。
2. **Python 写盘被拦**：任务文件夹（Downloads）和 `<system-temp>` 都 `PermissionError`，但 **pwsh 能写、Python 能写工作区 `<workspace>`**。→ 中间图一律落工作区，最终产物再用 pwsh 字节级复制。
3. **Node 脚本取参位置错了**：`process.argv[1]` 是脚本自身路径，参数在 `argv[2]`；错用会看到 `Unexpected token 'c', "const fs=r"... is not valid JSON` 这种"把源码当 JSON 解析"的怪报错。
4. **锚点越界**：`y + h` vs `y + h - 1` 差 1 像素，但对"图高 = bbox 底边"的 S028 就是 941 越界。→ 统一用最后一行像素。
5. **pwsh 控制台中文乱码**：`Get-Content`/标准输出按 GBK 解释会显示 ，**文件本身没问题**；要看内容用 `read` 工具。
6. **不能靠 alpha 分离图层**：合成图 alpha 全 255，任何"抠图再识别"的方案都会白跑。
