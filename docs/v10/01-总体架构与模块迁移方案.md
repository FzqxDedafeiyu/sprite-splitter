# V10 总体架构与模块迁移方案

> 文档状态：设计基线（Implementation Blueprint）
> 适用基线：精灵图切分编辑器 V9
> 目标：指导 Agent 将 V9 单文件工具渐进演进为 V10 精灵图生产工作台。
> 原则：先稳定数据与交互，再扩展动画工作区；保留已验证的图像处理算法。

## 1. 产品目标与范围

V10 从「精灵图切割编辑器」升级为本地优先的 2D 游戏素材生产工具，形成：

1. 图片导入与识别。
2. 自动 / 手工精灵图切割。
3. 元素管理与属性编辑。
4. 精修。
5. 场景布局与视差检视。
6. 动画校准与预览。
7. 质量检查和资源导出。

V10 必须同时满足：
- 保留 V9 已有且稳定的 Alpha 识别、背景抠除、矩形 / 多边形选区、GrabCut、分组属性、场景布局、视差检视、Agent JSON、PNG / JSON / ZIP 导出能力。
- 修复交互模式冲突、鼠标误触、指针取消后状态残留、数据更新后界面不同步、撤销覆盖不完整等架构性问题。
- 支持角色和物体两类动作组。
- 动画校准支持组级与单帧级双向切换。
- 角色枢轴按动作类型推荐，默认地面动作使用脚底中心，并允许切换骨盆、身体根节点、动作点等。
- 自动校准同时提供非破坏性预览和自动应用两种模式。
- 动画导出支持 PNG 序列 + JSON Manifest，以及 Sprite Sheet。
- 继续支持离线使用；AI 语义能力是可选增强，不得成为核心编辑链路的运行前提。

## 2. 非目标与约束

### 2.1 本轮不做的事
- 不为了模块化而重写图像分割、抠图、GrabCut 等算法。
- 不把场景锚点、动画枢轴、帧偏移合并成一个字段。
- 不将 Agent 建议直接写入用户数据。
- 不把某一个游戏引擎的数据格式作为内部唯一数据模型。
- 不在架构迁移阶段同时进行大规模视觉改版。
- 不以数组下标作为长期资源身份。

### 2.2 兼容性约束
- V9 项目文件必须可识别、可导入。
- 旧字段保留在迁移层解释，不应让新模块继续依赖旧字段语义。
- 迁移过程不得静默丢弃未知字段；无法映射的字段放入兼容扩展区并给出报告。
- 任何批量修改、自动校准、Agent 导入均须可整体撤销。
- 项目数据应可保存、关闭、重新打开并保持一致。

## 3. 当前 V9 架构基线与主要风险

V9 主体是单文件 HTML，界面、样式、业务算法、状态与事件处理集中在一个文件中。核心状态包含图片、sprites 数组、selected、zoom、addMode、lassoMode、refineMode、drag、history 等。

静态源码审查已识别的风险（运行时仍需测试确认）：

1. 交互模式由多个独立布尔值控制，非互斥，Canvas pointerdown 依赖 if 顺序决定优先级。
2. 自动识别等操作没有统一清理交互状态，可能残留套索或精修模式。
3. 指针生命周期未完整覆盖 pointercancel / lostpointercapture / window blur。
4. 多处直接修改 sprites 后手动调用 draw、refreshList、syncInspectorProperties 等，容易漏刷新。
5. Sprite 对象混合裁切几何、场景属性、动画相关潜在语义和 UI 状态。
6. 元素标识与数组索引耦合，排序或删除可能破坏外部引用。
7. 撤销快照覆盖不完整，部分删除、属性、Agent 导入、场景操作未形成统一历史事务。
8. 场景旋转绘制与命中检测坐标计算可能不一致。
9. 视差检视更新可能重复重建列表 DOM，拖动时存在性能风险。
10. 部分重叠清理逻辑可能使用与自动分割不同的像素归属结果。

以上问题应转化为回归测试，不应只依赖人工体验判断是否修复。

## 4. 目标架构

采用分层、模块化、单一数据源架构。建议逻辑分层如下：

```text
Application Shell
├── Workspace Layer
│   ├── Import / Detection Workspace
│   ├── Sprite Editing Workspace
│   ├── Inspector / Refinement Workspace
│   ├── Scene Layout Workspace
│   └── Animation Workspace
├── Application Services
│   ├── Interaction Manager
│   ├── Command Bus / History Manager
│   ├── Calibration Engine
│   ├── Quality Inspector
│   ├── Export Manager
│   └── Agent Adapter
├── Domain Layer
│   ├── Project
│   ├── Sprite Asset
│   ├── Scene Layout
│   ├── Animation Set / Clip / Frame
│   └── Pivot Presets
├── State Layer
│   ├── Reactive Store
│   ├── Selectors
│   └── Persistence
└── Infrastructure
    ├── Existing Image Algorithms
    ├── Canvas Renderer
    ├── File Import / Export
    └── Optional AI / Engine Adapters
```

### 4.1 模块职责与边界

| 模块 | 负责 | 不负责 |
|---|---|---|
| Sprite System | Sprite 身份、裁切几何、像素数据、分类与元数据 | 场景摆放、动画帧播放 |
| Scene Layout | 场景坐标、层级、视差、场景锚点 | 动画枢轴 |
| Animation System | 动作组、Clip、Frame、Pivot、Offset、FPS | 修改原始裁切几何 |
| Interaction Manager | 当前交互状态、指针捕获、取消与快捷键 | 业务数据持久化 |
| Reactive Store | 状态读写、订阅、派生选择器 | 绘制细节与图像算法 |
| Command / History | 统一数据修改、事务、撤销重做 | UI 组件状态 |
| Calibration Engine | 枢轴候选、帧对齐、偏移计算 | 未经确认直接覆盖用户数据 |
| Quality Inspector | 规则检查与问题定位 | 自动修复所有警告 |
| Export Manager | 通用资源导出、图集打包 | 内部动画数据的定义 |
| Agent Adapter | 外部建议的校验、预览、应用 | 绕过 Command 直接改 Store |

模块之间通过明确接口通信，禁止跨模块直接修改对方内部对象。

## 5. 技术栈与构建策略

建议目标采用 TypeScript + Vite 的模块化工程，以便拆分领域模型、交互逻辑、渲染器和工作区。

但「模块化源码」与「用户交付形态」是两个独立决策：
- 源码工程：建议 TypeScript + Vite。
- 交付形态：保留本地离线使用，可评估构建为单文件 HTML，或提供包含本地资源的离线 ZIP。
- 不得在尚未验证文件读取、Worker、字体、资源 URL 和浏览器兼容性前，承诺单文件构建必然无损。

实施前设置技术验证门：
1. 现有算法能否在模块化工程中复用。
2. 文件导入、下载、ZIP、Canvas、Worker 的构建后行为。
3. 离线环境下资源是否全部本地化。
4. 构建产物是否可直接打开，或是否需要本地静态服务器。
5. 是否能继续保留 Agent JSON 工作流。

在验证结果出来前，不把单文件 HTML 或多文件工程写死为唯一交付方式。

## 6. 领域数据模型总览

Project 是持久化根对象，至少包含：
- schemaVersion
- projectId
- assets / sprites
- sceneLayout
- animationSets
- pivotPresets
- projectSettings
- migrationMetadata

Sprite Asset 使用稳定 UUID，负责原始裁切素材和内容元数据。Scene Layout 和 Animation Frame 通过 spriteId 引用 Sprite，不复制其身份。

必须区分：
- sourceRect：原图中的裁切矩形。
- spriteLocal：Sprite 自身局部像素坐标。
- scene：场景世界坐标。
- animation：动作组参考画布坐标与帧局部坐标。

Scene Anchor 与 Animation Pivot 是不同领域概念，不共享字段。

详细动画数据协议见《02-Animation-System-技术规格》。

## 7. 状态与修改原则

1. Reactive Store 是应用状态的唯一权威来源。
2. UI 组件不持有第二份可独立修改的业务数据副本。
3. 业务数据只能通过 Command 修改。
4. Command 执行后产生可订阅的状态变更。
5. History 记录事务边界，而不是记录每次 pointermove。
6. 连续拖动在 pointerup 时提交为一个事务；pointercancel 时回滚或结束为明确的取消结果。
7. 派生数据通过 selector 计算，避免重复保存可推导字段。
8. Canvas 与面板从同一状态快照渲染。

## 8. 渐进迁移路线

### Phase 0：基线固化
- 保存 V9 原始版本与可回退副本。
- 建立代表性项目样本和回归素材。
- 记录当前算法输出与关键交互行为。
- 为已知问题建立可复现步骤。

交付：V9 Baseline、测试素材包、已知问题清单。

### Phase 1：领域模型与兼容层
- 定义 Project、SpriteAsset、SceneLayout 的类型。
- 为旧 Sprite 分配稳定 UUID。
- 写 V9 -> V10 Migration Adapter。
- 保留旧 JSON 导入导出兼容入口。
- 不改变切割算法行为。

验收：
- V9 样本可导入。
- 元素数量、裁切坐标、名称、分类、遮罩和场景属性无意外丢失。
- 导入后保存再打开结果一致。
- UUID 在保存、重排、删除其他元素后保持稳定。

### Phase 2：Interaction Manager
- 用互斥状态替代独立模式布尔值。
- 统一 pointerdown / move / up / cancel / lost capture / blur。
- 明确工具优先级和状态转换。
- 增加自动识别、切换工作区、导入等操作的交互清理策略。

验收：详见《03-Interaction-Manager 与 Reactive Store 技术规格》。

### Phase 3：Reactive Store 与 Command / History
- 建立单一 Store、订阅和 selector。
- 把高频 UI 更新与持久化数据更新分开。
- 建立 Command API。
- 覆盖所有会改变项目数据的操作。
- 支持事务、批量命令、撤销与重做。

### Phase 4：Animation Domain
- 实现 AnimationSet / Clip / Frame / PivotPreset。
- 定义坐标语义与预览渲染计算。
- 建立动作帧对 Sprite 的 UUID 引用。
- 建立校准来源和手工数据保护。
- 完成保存、加载和 schema 迁移。

### Phase 5：Animation Workspace
- 动作组管理、时间轴、中央预览、右侧属性。
- 组级和单帧级双向校准。
- 播放、暂停、逐帧、FPS、循环、洋葱皮。
- 使用 Interaction Manager 和 Command API，不建立私有交互体系。

### Phase 6：Calibration / QA / Export
- 几何候选与组级校准。
- 预览模式和自动应用模式。
- 质量检查报告。
- PNG 序列、JSON Manifest、Sprite Sheet。
- 预览与导出共用坐标计算内核。

### Phase 7：Agent 与引擎适配
- AI 语义枢轴建议。
- Agent 动作组建议和导入预览。
- Godot 等引擎适配器。
- 所有 Agent 输出经过 schema 校验、预览和 Command 应用。

## 9. 项目文件与版本迁移

建议 Project 文件使用显式 schemaVersion，例如：
- V9 legacy：由兼容层识别。
- V10 初始：schemaVersion = 10。

迁移规则：
1. 迁移前保留原始数据快照。
2. 迁移过程纯函数化：输入旧数据，输出新数据和 warnings。
3. UUID 在同一项目内唯一；迁移时可生成并持久化。
4. 旧 anchor 不能自动推断为 Animation Pivot。
5. 旧 anchor 按 V9 实际语义映射为 sceneAnchor 或 legacyAnchor，并记录来源；不确定时保留为扩展字段。
6. 未知字段放入 legacyExtensions，不能静默删除。
7. 迁移报告列出成功、警告、无法自动映射项目。
8. 不覆盖原始文件；用户确认后另存为 V10 项目。

## 10. 测试与验收矩阵

| 范围 | 必测内容 |
|---|---|
| 导入 | 透明 PNG、不透明底图、异常尺寸、损坏文件 |
| 切割 | Alpha 连通域、手工矩形、多边形、背景抠除、GrabCut |
| 身份 | UUID 稳定性、引用完整性、重排与删除 |
| 场景 | 锚点、旋转、层级、锁定、视差、命中测试 |
| 状态 | 多面板同步、快速切换工作区、连续编辑 |
| 历史 | 单次操作撤销、批量事务撤销、撤销后重做 |
| 指针 | pointercancel、失焦、失去捕获、窗口尺寸变化 |
| 动画 | 组级校准、单帧覆盖、播放、循环、帧时长 |
| 导出 | PNG 序列、Manifest、Atlas 坐标与 Pivot |
| 兼容 | V9 导入、V10 保存重开、未知字段保留 |
| 离线 | 断网启动、导入、编辑、保存和导出 |

## 11. Agent 实施约束

Agent 每个阶段必须：
1. 先阅读本目录三份规格和 V9 基线文件。
2. 明确本阶段允许修改的模块和禁止修改的算法。
3. 先给出实施计划和受影响文件清单。
4. 小步提交，不在一个任务中同时重写多个核心系统。
5. 为每个新增行为提供自动化测试或可复现手工验收步骤。
6. 不得为了通过测试而删除旧功能。
7. 每阶段结束提供变更摘要、测试结果、已知限制和回滚方式。
8. 未经明确授权，不得直接把实验性版本替换为正式 V9 文件。

## 12. V10 阶段完成定义

V10 不是以「界面看起来完整」作为完成标准。至少满足：
- V9 项目可迁移。
- 原有图像算法回归通过。
- 交互状态不冲突，指针异常能恢复。
- 多面板由统一 Store 同步。
- 数据修改有一致的撤销 / 重做。
- 动画数据能保存和重开。
- 组级 / 单帧校准能互相配合。
- 自动校准不覆盖手工结果。
- 预览和导出位置一致。
- PNG 序列、JSON、Sprite Sheet 可重新验证。
- 离线核心流程可用。
